# Payment Service

Independent Java 17 / Spring Boot 3.5.7 learning microservice for bus booking payments.
Payments transition from PENDING to simulated SUCCESS or FAILED. No money is
transferred and no real payment gateway or credential storage is implemented.
Booking IDs are external references, not foreign keys to another service's database.

## Run and test

From this directory, with Java 17 or later installed:

Set `INTERNAL_SERVICE_TOKEN` to the same nonblank value used by Booking Service
before starting. Seat uses the same token. Start Bus, Seat and Booking first.
See the [integration guide](../../README.md).

```powershell
.\mvnw.cmd clean verify
.\mvnw.cmd spring-boot:run
```

The API runs on port 8083. Swagger UI: http://localhost:8083/swagger-ui.html
OpenAPI JSON: http://localhost:8083/v3/api-docs
H2 console: http://localhost:8083/h2-console

The local database URL is `jdbc:h2:file:./data/paymentdb;MODE=PostgreSQL;DB_CLOSE_ON_EXIT=FALSE`.
Its location is relative to the process working directory. Local username defaults to
`sa` and the password is empty. Override using `PAYMENT_DB_USERNAME` and
`PAYMENT_DB_PASSWORD`; do not commit production secrets.

## API

| Method | Path | Result |
| --- | --- | --- |
| POST | /api/payments | 201, simulated payment result, Location header |
| GET | /api/payments | 200, payment array |
| GET | /api/payments/{id} | 200, payment or 404 |
| GET | /api/payments/booking/{bookingId} | 200, payment array (empty if none) |
| POST | /api/payments/{id}/confirm-booking | 200, retry confirmation for SUCCESS only |
| POST | /api/payments/{id}/notify-booking | 200, retry SUCCESS confirmation or FAILED release |

Example POST body:

```json
{"bookingId":42,"paymentMethod":"UPI"}
```

Methods: UPI, CARD, NET_BANKING. Booking Service provides the authoritative amount;
an optional legacy amount is validated but ignored. Unknown fields are rejected,
including transactionId, paymentStatus, paymentDate and any credential fields.
Transaction IDs are UUIDs generated by the service. Payment date records request creation
in the server's local time, not settlement time. Booking must exist, be
PENDING_PAYMENT (or legacy PENDING), and not have a past journey date. New holds
must have an unexpired reservation timestamp. An existing PENDING or SUCCESS
attempt causes 409 on repeat creation. Failed new seat-backed bookings release
their holds and need a new booking before another payment.
The duplicate check is serialized in a single instance, not across replicas.

`services.booking.url` / `BOOKING_SERVICE_URL` defaults to http://localhost:8082.
RestTemplate uses 3-second connect and 5-second read timeouts. Simulation succeeds
by default; set `PAYMENT_SIMULATION_SUCCESS=false` to persist FAILED without
confirming Booking, then notify Booking to release seats. This is server
configuration, not a frontend request option. Payment never calls Seat directly.

Errors contain timestamp, status, error, message and path. Unexpected failures use a
generic message without stack traces or internal details.

## Tests and deployment boundaries

PaymentApiTests exercises the controller, service and repository together using
MockMvc and an isolated in-memory H2 database, never the local file database.
It covers persistence, all four endpoints, supported methods, unique transaction
IDs, validation, malformed requests, unknown fields, missing payments and Swagger.

SUCCESS is persisted before Booking is notified. If notification fails, the API
returns an error but the payment remains SUCCESS. Look up payments by booking ID,
then retry `/api/payments/{id}/confirm-booking`; do not create another payment.
Both outcomes persist `notificationPending`; a 30-second worker retries until
Booking acknowledges. Configure `payments.recovery-enabled` and
`payments.recovery-delay-ms`. There is no distributed transaction or refund flow.
SUCCESS arriving after expiry cannot recreate a hold and needs operator reconciliation.
PENDING records left by a process crash require reconciliation. Even SUCCESS
here is simulation only, not evidence that real funds were settled.

This configuration is for local learning, not an internet-facing payment system.
Before production, add authentication/authorization, external secret management,
database migrations instead of ddl-auto=update, operational monitoring and an actual
provider integration with verified callbacks and idempotency. Disable the H2 console,
SQL logging and public Swagger access. Never collect card numbers, CVV, UPI PINs,
passwords or banking credentials in this service.
